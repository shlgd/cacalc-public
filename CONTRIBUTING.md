# Изменения проекта

Сначала прочитайте [архитектуру](docs/architecture.md) и
[инструкцию сборки](docs/getting-started.md). Обсуждения и документация —
на русском; идентификаторы и имена файлов — на английском.

Один PR должен решать понятную задачу. Опишите пользовательское действие,
что изменилось и чем это проверено. Сохраняйте локальный ввод, черновики,
прошлые снимки питания и независимость каталога от личных данных.

Не добавляйте комментарии в код; поясняйте решения в описании PR или
документации. Существующие комментарии не удаляйте без относящейся к ним задачи.
Изменение формата хранения требует версии схемы, миграции и воспроизводимой
проверки на временных данных. Не подставляйте нули вместо неизвестных значений.

Для изменения интерфейса опишите затронутый путь и состояния, проверьте
длинные русские подписи, доступность и прокрутку. Изменения кнопок сохраняют
controlID, новые действия добавляются в `docs/usage-controls.json`.

Обычные тесты должны работать без сети и платных API. Не используйте личную
базу для тестов и не коммитьте реальные диктовки, логи или данные Health.
Проверьте `git diff --cached` и состав файлов перед отправкой.

Публичный снимок имеет `PUBLIC-MANIFEST.json` с перечнем и SHA-256 файлов.
Он фиксирует конкретную подготовленную версию. При следующих изменениях
пересоздайте его после проверки состава; несовпадение должно останавливать
публикацию. Для обычного развивающегося checkout проверяйте новые изменения
и секреты отдельно, не считайте старую квитанцию разрешением на новые файлы.

Проверка снимка и поиск секретов выполняются локально:

```sh
python3 -B tools/check_public_release.py
gitleaks dir --redact=100 --no-banner .
```

При Git-публикации дополнительно проверьте историю и автора:

```sh
gitleaks git --redact=100 --no-banner --log-opts=--all .
git log --all --format='%h %an <%ae> %s'
git remote -v
```

Публичные изменения не должны объединяться с историей приватной разработки.
